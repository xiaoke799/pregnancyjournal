# issue 关闭话术

> 关闭 issue 前贴一段说明：**改了什么、从哪个版本起可用、还不行怎么反馈**。
> 直接点 Close 不说原因，用户升级后发现没修，就再也不会反馈了。
>
> 本文件是话术库，不是规则。真正的事实来源是 `docs/known-issues.md`（状态/版本/修复提交）。

## 一、什么时候**不该**关

判断标准只有一条：**用户升级到最新发布版后，他报的现象还会不会复现**。

- 修复代码在仓库里但**没发布** ⇒ 不关（用户拿不到）
- 修复在 PR 里但**没合并** ⇒ 不关
- 只修了同类问题的一部分 ⇒ 不关，或者关之前把剩下的拆成新 issue
- 报的是"设计如此" ⇒ 可以关，但要写清为什么不做（附既定口径）

反例（2026-11-10 真实遇到）：issue #3 报了四处时区问题，四处都在 PR #5 里、**PR 未合并**；
另有同源一处在 0.0.35 里、**包未发布**。此时关闭 = 用户升级后发现仍差 8 小时、且无处反馈。

## 二、通用结构

```
已在 <版本> 修复，此处关闭。感谢反馈。

**根因**：<一句话说清为什么会发生，不要写"优化了一下">

**修法**：<改了什么；有护栏的话提一句，让后来者知道这类问题有断言盯着>

**影响面**：<还涉及哪些同类场景，一并说明>

升级到 <版本> 或更高版本即可。若仍能复现，欢迎新开 issue 并附应用版本与复现步骤 —— 关门不等于不再跟进。
```

```
已在 0.0.33 修复，此处关闭。感谢反馈。

根因：分类切换用的单选组件绑定了错误的属性名 —— naive-ui 没有 modelValue 约定

（类型定义 / 全项目扫描 / 编译产物 / 真实渲染）。

升级到 0.0.33 或更高版本即可。若仍有分类打不开，欢迎新开 issue 并附应用版本。
```

### #1 上传检查报告失败（状态：已关 / 0.0.28）

```
已在 0.0.28 修复并发布，此处关闭。感谢反馈。

你这条里提到了四个问题，对照现在的实现逐条说明：
- 设备上传失败：单文件限 50MB，仅支持 JPEG/PNG/WebP/HEIC/PDF，超限或格式不符会明确报错
- NAS 取不到目录：目录浏览走路径白名单校验，越界路径会被拒绝

- 导出提示成功但找不到文件：产物目录可在设置页确认/指定
- 微信推送提醒：属推送配置侧，需看具体配置

若升级到 0.0.35 后任何一条仍能复现，欢迎新开 issue —— 关门不等于不再跟进。
```

## 四、批量关

Issues 列表页勾选 → `Mark as completed`：
<https://github.com/xiaoke799/pregnancyjournal/issues>

关闭原因选择：修复完成 → `completed`；不打算做 → `not_planned`；重复 → `duplicate`（并填原 issue 号）。

## 五、用脚本关闭（需要 PAT）

连接器的 OAuth scope 可能只读（写会 403），所以关闭走 PAT 直连：

```bash
# 1. 建 fine-grained PAT：Issues = Read and write、Pull requests = Read and write、Contents = Read
#    只勾 pregnancyjournal 这一个仓库
# 2. 存到仓库外（别提交，也别贴聊天里）
echo 'github_pat_xxx' > ~/.workbuddy/github-token

# 3. 预演：只打印，不改任何东西
GITHUB_TOKEN=$(cat ~/.workbuddy/github-token) node tools/ci/close-issue.js --issue=2 --dry-run

# 4. 真的关（把话术一起贴上去）
GITHUB_TOKEN=$(cat ~/.workbuddy/github-token) \
  node tools/ci/close-issue.js --issue=2 --reason=completed --comment-file=/tmp/reply-2.md
```

- 批量：`--issues=1,2`
- `--reason`：`completed`（修好了）/ `not_planned`（不做）/ `duplicate`（重复）
- 幂等：已经关闭的会跳过，不报错
- 传 PR 号会提示「这是 PR，不是 issue」并跳过

## 六、为什么这些事没让机器人做

自动化里的 `issue-triage.js` 只**分类和首回**，不关 issue。原因：

- 关闭是不可逆的对外动作，判据是"是否已发布"，而机器人不知道发布状态
  （`manifest` 里只有版本号，没有"已上架"这个事实）。
- 一旦机器人误关，用户看到的是"官方说修好了"，比不回复更伤。

要让它能判断，需要一个"已上架版本"的真源（例如一个 `docs/released.json`，由发版流程写入）。
那件事没做，所以关 issue 保持人工。
