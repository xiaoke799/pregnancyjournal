# 仓库工作流

> 一句话：**规则在仓库里、证据可判定、红灯拦得住。**
>
> 这套东西不是为了"看起来很工程化"，而是针对本仓库三个已经发生的事实：
> ① 项目的全部经验（几十条铁律）曾只存在本机一个**不入库**的目录里，clone 下来等于零；
> ② 81 套回归很强，但"跑不跑"全凭人记得；
> ③ 回归运行器有红灯时**退出码仍是 0** —— 直接接 CI 会在一片红里报绿。

## 一、结构：三层规则 + 一道闸门

```
                ┌─────────────────────────────────────────┐
   入口层 L1    │ AGENTS.md  只指路，不装规则（~50 行）    │
                │   ↳ CLAUDE.md 一行转发（别在这里加东西） │
                └───────────────┬─────────────────────────┘
                                │ 按"我要做什么"分流
        ┌───────────────────────┼────────────────────────┐
        ▼                       ▼                        ▼
┌───────────────┐   ┌────────────────────┐   ┌──────────────────────┐
│ L2 错题本     │   │ L3 硬化规范        │   │ 验证能力             │
│ LESSONS.md    │──▶│ docs/code-         │   │ tools/verify/        │
│ 带 Seen 次数  │3× │ standards.md       │   │ 81 套 + gate.js      │
│ 还在观察的坑  │升 │ 每条挂护栏或[人审] │   │ + lessons.js         │
└───────────────┘格 └────────────────────┘   └──────────────────────┘
        ▲                                              │
        └──────────── 踩到新坑就回来记一条 ─────────────┘
```

三层各管一件事，混在一起就全废：

| 层 | 文件 | 只放什么 | 明确不放什么 |
|---|---|---|---|
| L1 | `AGENTS.md` | 路由表 + 3 条不可协商 | 具体规则（堆进来会稀释注意力） |
| L2 | `LESSONS.md` | 返工过 / 假绿过 / 差点漏掉的坑 | "最佳实践"、没出过事的建议 |
| L3 | `docs/code-standards.md` | 已转正、**挂得上护栏**的规则 | 挂不上护栏又说不清怎么人审的规则 |

## 二、规则怎么生长（这是整套东西的核心）

```
新坑 ──写一条──▶ LESSONS.md (Seen 1×, OPEN)
                      │
                      │ 同一个坑再次被捕获（夜审 / 回归红 / 线上）⇒ Seen +1
                      ▼
                 Seen 3× ?
                      │
        ┌─────────────┴─────────────┐
        ▼                           ▼
  值得硬化                     不值得（偶发/环境特有）
        │                           │
        ▼                           ▼
  搬进 code-standards         标 RETIRED + 写理由
  + 挂一个护栏脚本            （明确"不硬化"，而不是含糊留着）
  + LESSONS 标 PROMOTED → #CS-NN
```

`node tools/verify/lessons.js` 把这条链变成机器检查：

- `Seen ≥ 3×` 还是 `OPEN` ⇒ **判红**（强制二选一，不许含糊挂着）
- 标了 `PROMOTED` 却没给 `#CS-NN`，或那个小节不存在 ⇒ **判红**（引用悬空 = 没写）
- 缺「症状/根因/判据/证据」任一字段 ⇒ **判红**（没证据的条目等于没发生）
- `RETIRED` 必须写理由（否则看起来像在逃）

> 为什么强调"证据"字段：这个仓库历史上出现过"因为写了检查所以认为安全"的假绿，
> 也出现过"红了但红在 MODULE_NOT_FOUND"的假反例。**没有证据的结论，一律当作没有结论。**

## 三、一次改动（日常）

```bash
# 1. 改代码
# 2. 闸门：按 diff 自动选套件（通常 1~3 套，几十秒）
node tools/verify/gate.js

# 3. 自审：这次的断言撤掉修复会不会红？故意改坏一处会不会报警？
#    口径见 docs/review-protocol.md（Red Check / Break Check）

# 4. 提交，带证据块
git commit -m "fix(...): ...

verify:
  red-check:   ...
  suites:      verify_pkg_versions(11/0) ...
  not-run:     ...
"
```

`gate.js` 做的事：读 `git diff HEAD` + 未跟踪文件 → 命中 `RULES` → 只跑受影响的套件 → **红则退出码 1**。
它把 `tools/verify/README.md` 里那张"改什么必跑什么"的表变成了代码 —— 表是给人看的，代码是会被执行的。

可选：把闸门装成 `pre-commit`（`node tools/verify/install_hooks.js`）。
默认不装 —— 本仓库多会话并行是常态，钩子拦到别人头上会让人养成 `--no-verify` 的肌肉记忆，那比不装更糟。

## 四、一次发版

```bash
# 1. 全量回归（这块只能在本机跑：要真后端 + 无头浏览器 + app/ui 产物）
node tools/verify/run_all_suites.js

# 2. 版本号 8 处同步（manifest 是唯一真源）→ 重建前端产物 → 打包
#    详见 DEPLOY_NOTES.md；改完 manifest 必须 cd frontend && npm run build

# 3. 发版闸门：tag ≡ manifest.version ≡ CHANGELOG 小节 ≡ manifest.changelog
node tools/verify/gate.js release --tag=v0.0.34

# 4. 打 tag 并推；CI 的 release job 会用 tag 名再校验一遍（同一份判定，不是两套）
git tag v0.0.34 && git push origin v0.0.34
```

第 3 步的四项对齐，此前**没有任何一处校验**：`verify_pkg_versions.js` 只管 `package.json / lock`，
`build.ps1` 只管它那 5 处 —— 「tag 名」和「CHANGELOG 小节」两条链是断的。
补上它的意义：`v0.0.34` 的 fpk 里装的必须是 0.0.34，而不是"大概是吧"。

## 五、CI 为什么只跑六套

| 层 | 跑什么 | 为什么到这里为止 |
|---|---|---|
| `static` | 版本同步 / 路由契约 / 深色接线 / 主题令牌 / 错题本 / 产物卫生 | 零外部依赖，秒级，稳定 |
| `frontend` | 类型体检(vue-tsc) / naive-ui 绑定契约 | 只需 `frontend/node_modules` |
| `release` | tag 一致性（仅 tag 触发） | 与本地 `gate.js release` 同一份判定 |

全量 81 套**有意不进 CI**：其中大量套件要真起后端、要无头浏览器、要 `app/ui` 构建产物，
而 `app/ui` 是 gitignore 的（构建产物不入库）—— 塞进 CI 只会得到一屏常红，然后没人再看。
**常红的检查和没有检查是等价的**，这条比"CI 覆盖率好看"重要。

真要在 CI 里扩，口径是：先在 Linux 上实测跑绿，再往 `verify.yml` 加一套；一次只加一套。

## 六、物理急刹（并发取消）

```yaml
concurrency:
  group: verify-${{ github.ref }}
  cancel-in-progress: ${{ !(startsWith(github.ref, 'refs/heads/master') || startsWith(github.ref, 'refs/tags/v')) }}
```

默认的 `cancel-in-progress: true` 会让"上一轮还没跑完就被下一次 push 掐断"变成常态，
连续几个版本谁都没真正跑完，而界面看起来一直在跑。**main 与 tag 上必须跑完整轮**，
PR 分支允许取消（同一分支连推只保留最新一轮）。

## 七、自动化：PR 审查 / 自动合并 / issue 回复

前面几节讲的是"人怎么按规矩做事"。这一节是**让机器替人做掉那部分可判定的工作**：

| 事件 | 机器人做什么 |
|---|---|
| 新 PR / 新提交 | 硬检查（高危路径、规模、提交规范、产物混入）+ 规则映射（该跑哪些套件）+ 模型审查 → 贴/更新一条评论，打 `review:pass` / `review:changes` / `review:needs-human` |
| PR 有 `automerge` 且检查全绿 | squash 合并 + 删分支 + 留言 |
| 新 issue | 分类打标 + 首回（事实只来自 `docs/known-issues.md`） |
| 评论发 `/review` `/triage` `/merge` | 重跑对应流程（仅维护者） |

三条设计红线（都在 `docs/workflow-automation.md` 里展开）：

1. **不执行 PR 的代码**。`pull_request_target` 有写权限，所以 checkout 只取默认分支，
   PR 的 diff 只当文本读。这条破了就是提权漏洞。
2. **模型只能加严，不能放宽**。硬检查判定"高危路径要人看"，模型说没问题也不改判。
3. **自动合并需要人显式授权**（`automerge` 标签）。机器不自己决定边界。

机器人自己也有回归：`tools/ci/selftest.js`（已进汇总运行器），
覆盖判定方向、降级行为、prompt 注入、已知问题解析完整性。

## 八、人保留的三道闸门

工作流能自动化"检查"，替代不了"决定"。这三件事仍然必须由人拍板：

1. **真机验证**：无头浏览器验不了插入符（`F7` 插入符浏览）、验不了移动端 WebView 反色、
   验不了 fnOS 上安装/升级。这类改动必须上真机，且结果写进证据块。
2. **不可逆决策**：目录结构（`TRIM_APPDEST` 覆盖 / `TRIM_PKGVAR` 持久）、数据迁移方向、
   上架口径。已经拍板的（如"零隔离、家庭共用"）不许被后续改动"顺手优化"掉。
3. **审美与文案**：配色、排版的"对不对"没有断言能表达。这类只能人看，且看的人要给出具体意见
   （"这个间距 4px 太挤"），而不是"感觉不对"。

## 九、这套东西不做什么（避免误解）

- **不保证没有 Bug。** 它保证的是"已知的坑不会以同样的方式再踩一次"。
- **不替代真机验证。** 静态断言只能钉住"接线通不通"，钉不住"在 fnOS 的 WebView 里长什么样"。
- **不追求覆盖率。** 没有"必须 80%"这种指标 —— 本项目历史上更有价值的是一批**针对性**断言
  （压线阈值、空会话不清零、UTC 差一天），而不是一堆走 happy path 的用例。
- **不阻止你跳过。** `--no-verify` 永远可用。它只是让"跳过"这件事**必须留下痕迹**。

## 十、已知缺口（诚实清单）

| 缺口 | 现状 | 怎么补 |
|---|---|---|
| 全量回归不在 CI | 需真后端/浏览器/产物，只能在开发机跑 | 若将来有 Linux 构建机，可把 e2e 层接进去 |
| 夜审没有自动化 | 现在靠人/会话收尾时 `--bump` | 可挂一个定时任务：跑 `lessons.js` + 全量回归，异常才叫人 |
| 错题本条目来自历史铁律回填 | `Seen` 次数按历史记录回填，非逐次统计 | 以后每次捕获用 `--bump` 累计，才是真实次数 |
| `gate.js` 的规则表靠人工维护 | 新增模块目录不会自动进规则 | 每次新增 `routes/` `services/` 子模块时补一条；漏了会打印"未命中规则"提醒 |
