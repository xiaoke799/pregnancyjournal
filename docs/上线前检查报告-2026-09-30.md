## 四、后端数据层专项审查（另一类阻塞：静默丢数据）

> 本节的 D1 / D2 与第二章的三个安全问题**同级**，都应视为**发布阻塞项** ——
> 它们使用户在界面明确提示「保存成功」之后，仍然**永久丢失不可重新采集的孕期记录**。

### 🔴 D1 · 业务写入不落盘，硬停丢最多 30 秒已确认数据（已复现）

**位置**：`app/server/node/db.js:878`、`app/server/node/server.js:342-353`

落盘只有两条路径：**30 秒定时器**（`db.js:878` `setInterval(saveDbAsync, 30000)`）与 **SIGTERM/SIGINT**（`server.js:342-353`）。
**没有任何业务路由在写入后调用 `saveDb()`** —— 我已独立核实全库调用点，`saveDb()` 仅 12 处：

| 调用点 | 用途 |
|---|---|
| `db.js:868` | 启动初始化末尾 |
| `db.js:878` | 30 秒定时器 |
| `server.js:326 / 334 / 345` | uncaughtException / unhandledRejection / 优雅退出 |
| `export.js:515 / 603 / 692 / 726 / 1160 / 2125` | 备份、恢复、导入前后 |
| `media-backfill.js:190 / 205 / 212` | 媒体补齐 |

**实测复现**：

```
POST /daily-records   → http=200  code=0  message=success
紧随 200 之后读盘     → {"pregnancy":1,"daily_record":0}
硬杀进程后再读盘      → {"pregnancy":1,"daily_record":0}
3 条 POST 全部 code=0，硬杀后盘上只剩 1 条
```

**真实触发场景**：

- NAS 内存不足，OOM killer 直接 SIGKILL
- 拔电 / 强制断电
- **应用自己的卸载流程**：`cmd/uninstall_callback:15` 在 `pkill -TERM` 后**只等 2 秒**就 `pkill -KILL` ⇒ 这 30 秒窗口内的数据必丢

**为什么回归套件没发现**：套件收尾用 `SIGKILL` 前往往已跨过定时器周期，或走的是优雅退出路径，因此 `verify_db_persist.js` 保持全绿。

**修复**：commit 之后立即 `saveDb()`（库约 300 KB，代价可忽略），或引入脏标记 + `setImmediate` 合并写。

> ⚠️ **对早先判断的更正**：`db.js:970-973` 的 `_writeSeq`「防旧快照回退」护栏**几乎从未被触发** ——
> 因为业务路径从不调用 `saveDb()`，序号根本不会变。结论「不会回退」依然成立，但**并非靠这个护栏**。
> 真正起作用的是 `tmp + rename` 的原子性与 `_txDepth` 互斥。

### 🔴 D2 · `writeTable()` 逐行吞异常，恢复/导入报的成功条数是假的（已复现）

**位置**：`app/server/node/routes/export.js:302-314`，调用点 `:1045`（`/restore`）、`:510` / `:546`（import-json / import-dir）

```js
for (const row of rows) {
  const sanitized = sanitizeColumns(table, row);
  if (!sanitized || Object.keys(sanitized).length === 0) continue;   // 静默跳过
  ...
  try { db.run(sql, ...); count++; } catch (e) { log.warn('导入', ...); }  // 吞掉异常但仍计数
}
```

**实测复现**：归档含 3 行 `daily_record`（1 行合法、1 行 `record_date: null` 违反 NOT NULL、1 行 FK 孤儿）

```
→ http=200  code=0  total_rows=1  message="恢复完成: 1 条记录, 0 个文件"
>>> 接口报成功，但 3 行里有 2 行被丢弃
```

`import-json` 同样：送 3 行孤儿 → `{"code":0,"total_rows":0,"message":"导入完成: 0 条记录"}`

**为什么这条特别危险**：用户在恢复前通常**已经清空了当前数据**。若 `pregnancy` 父行因任何原因没写进去，
该孕期的**所有子表都会被外键挡掉**，而界面显示「恢复完成」⇒ 两头落空。

**修复**：任一行失败即 `throw`（`/restore` 有事务，会整体回滚）；响应体区分 `imported` 与 `failed`，不要把「尝试数」当「成功数」。

### 🟠 D3 · 启动迁移无迁移前备份，且结果立即落盘（不可回滚）

**位置**：`app/server/node/db.js:863-868`

`applySchemaAndMigrate()` → `saveDb()`。启动自检只保护「库**已经**损坏」，对「库没坏但**迁移改坏了**」零保护：

- `_repairCheckupIdFks()` 会 `DROP` + 重建三张表（`db.js:560-568`）；失败时只回滚 + 关闭外键强制，**不落备份、不中止启动**
- `migrateDb()` 的 `ADD COLUMN` 与随后回填 `UPDATE` 是**两条独立语句**（`db.js:626-629`），无事务包裹 ⇒ 中断即留半迁移态
- 而下次启动会**跳过**已不匹配的表（`db.js:551`），且只补缺失列 ⇒ **不能自愈**

**修复**：迁移前用现成的 `_probeDbFile()` 探活后 `copyFileSync` 一份 `.premigrate-<时间戳>`（一行代码），并把 ADD + 回填包进事务。

### 🟠 D4 · v0.0.28 的类型错误被固化，无法修正

v0.0.28 的 `migrateDb` 硬编码 `ADD COLUMN ... TEXT`，而同批新增了 `daily_record.waist`。
`declaredColumnType()` 的修复逻辑**只作用于「缺失的列」**（`db.js:622` 仅 ADD 缺失列）⇒ **已存在列的类型永不修正**。

已复现：构造成 v0.0.28 升级后的库形状 → `on-disk SQLite types: [["text","80","real",90]]`
⇒ 腰围按**字符串**存储、胸围按**数字**存储。**所有经 v0.0.28 升级的用户都受影响。**

**修复**：补一次类型修复迁移，复用 `_repairCheckupIdFks()` 那套「显式列名 + 行数 + 内容摘要」的安全重建。
